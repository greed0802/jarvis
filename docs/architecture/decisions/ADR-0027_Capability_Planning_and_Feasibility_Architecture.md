# ADR-0027: Capability Planning and Feasibility Architecture

**Status:** FROZEN
**Frozen Date:** 2026-07-28
**Date:** 2026-07-28
**Authors:** Architecture Workstream
**Related Reviews:** EQ-0023 (Spike 2)

---

## Context & Problem Statement

The Planner Engine must determine what capabilities are available and whether they can satisfy the requirements of an execution plan. Without a governed architecture, the Planner may query live capability registries during plan composition, creating race conditions when capabilities upgrade, degrade, or are removed mid-planning. This introduces non-deterministic execution drift where two identical planning requests produce different feasibility outcomes.

This ADR codifies the authority relationship between the Planner Engine and the Capability Registry, the immutability of capability snapshots, and the strict separation of feasibility evaluation from capability selection — as approved by the Project Owner in the frozen EQ-0023 Architecture Review.

---

## Decision Drivers

- Planning must be deterministic: identical starting conditions must yield identical feasibility evaluations.
- Planner Engine must not depend on live registry state during plan composition.
- Capability Registry is the sole system of record for capability metadata.
- Feasibility is a binary gate, not a recommendation engine.

---

## Decision Outcome

### Read-Only Planner Model

The **Planner Engine** has **strictly read-only** access to capability metadata. It may consult a `CapabilitySnapshot` but **SHALL NOT** directly query the live capability registry. The Planner plans; the Registry records.

### Registry Sovereignty

The **Capability Registry** is the sole authoritative system of record for capability metadata. It is the exclusive owner of:
- Capability registration and versioning
- Schema and interface definitions
- Topology rules and constraint models
- Snapshot generation on behalf of the Planner

### Versioned CapabilitySnapshot

Planning operates exclusively on a **versioned, immutable `CapabilitySnapshot`** generated by the Capability Registry at plan initiation.

Snapshot structure:
| Field | Description |
|-------|-------------|
| `snapshot_id` | Unique version identifier |
| `registry_version` | Version of registry at snapshot creation |
| `created_at` | Timestamp of creation |
| `capabilities` | Immutable list of capability records |
| `constraints` | Constraint models (schemas, availability, inter-dependencies) |
| `hashes` | Cryptographic hashes for integrity verification |

The snapshot is injected into Context and becomes part of the execution plan's deterministic boundary.

### Strict Feasibility Boundary

**Feasibility SHALL determine only whether a capability satisfies required binary constraints.**

- Feasibility = `TRUE` / `FALSE` on constraint satisfaction.
- Feasibility evaluates: capability *exists*, schema is *compatible*, constraints are *satisfied*.
- Feasibility does NOT evaluate: which capability is *best*, most *popular*, most *performant*, or most *preferred*.

**Capability selection, ranking, and optimization are separate architectural concerns and SHALL NOT influence feasibility calculations.**

---

## Architectural Commitments

1. **Registry Sovereignty**: Capability metadata originates from and is owned exclusively by the Capability Registry.
2. **Immutable Snapshot**: Planning operates on point-in-time immutable snapshots, not live queries.
3. **Read-Only Planner**: The Planner Engine has zero write access to capability state.
4. **Binary Feasibility**: Feasibility is a deterministic TRUE/FALSE gate, not a scoring function.

---

## Architectural Invariants

- **Invariant 2.1:** The Planner Engine SHALL NOT query the live capability registry during plan composition.
- **Invariant 2.2:** The `CapabilitySnapshot` SHALL be immutable once injected into Context.
- **Invariant 2.3:** Feasibility SHALL determine only whether a capability satisfies required constraints; selection, ranking, or optimization are separate architectural concerns and SHALL NOT influence feasibility.
- **Invariant 2.4:** Every execution plan SHALL reference exactly one `CapabilitySnapshot` throughout its planning lifecycle.

**Total Invariants:** 4

---

## Consequences

### Positive
- **Deterministic planning**: Identical planning requests result in identical feasibility evaluations.
- **Race-condition immunity**: Planner never reads live, mutable registry state.
- **Clear separation of concerns**: Registry owns capability state; Planner owns strategy; Feasibility is a mechanical check.
- **Traceability**: Every plan links to its exact capability state via the snapshot version.

### Negative
- **Snapshots become stale**: Capability drift between snapshot creation and execution *must* be detected at Preflight validation time (see ADR-0028).
- **Snapshot storage overhead**: Each plan stores a copy of the snapshot rather than referencing a live view.
- **Registry availability requirement**: Snapshot generation requires the Capability Registry to be available at plan initiation.

## Explicit Deferrals (Implementation Scope, Non-ADR)

The following items are implementation concerns intentionally deferred from this ADR:

| Item | Rationale |
|------|-----------|
| Exact query syntax for filtering capabilities | Implementation detail; architectural constraints provide sufficient boundaries |
| Catalog caching algorithms and memory optimization | Not an architecture decision; performance optimization |
| Distributed catalog synchronization across nodes | Subject to infrastructure topology; not a planning immutability concern |
